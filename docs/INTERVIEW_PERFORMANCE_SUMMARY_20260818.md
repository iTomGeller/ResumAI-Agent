以下数字来自真实压测原始结果，未把容量估算当成实测：

| 指标 | 实测值 | 口径 |
|---|---:|---|

## 延迟优化结果

12 份修复回归 smoke 中：

- 简历 RAG P95：约 41.5s → 154.7ms；
- Run permit 重获取 P95：约 39.7s → 20.8ms；
- Runtime P95：约 247.6s → 86.9s；
- 12/12 SUCCESS，未出现 FAILED 或超时。

这批只有 12 份，不能用来宣称新的稳态吞吐，只用于验证延迟修复。

## ReportAgent v8 延迟优化（尚未重新付费压测）

历史 smoke 中 ReportAgent P50/P95 约为 49.6/57.2s，是当前关键路径最大节点。代码已做以下收敛：

- 共享状态 prompt view：最多 9,000 → 6,000 字符；
- Report 知识库 RAG：Top-5/最多 6,000 → Top-3/最多 2,800 字符；
- 最大输出：4,096 → 3,072 tokens；
- 删除 function schema 中下游未使用的 `followUps`、`scoreRubric`、风险 `confidence/impact`；
- 评分维度固定4个，优势2-4条，风险1-4条，追问4-6题，每项最多2个证据引用；
- 完整评估不再把可能很长的原始 user message 重复附加给终态 ReportAgent。
- 正常、完整的上游 artifact 只需汇总，ReportAgent 使用 Flash；仅在上游失败、artifact 冲突/缺失或必要输入缺失时确定性升级 Pro。

这些是代码与本地 schema/validator 验证结果，不是新的线上时延实测；没有为此调用业务 LLM。

## 1 QPS 容量模型

完整 Workflow 的 1 QPS 是容量目标，不是当前单机实测值。

以单分片实测 `0.2704 份/s` 为基准，假设使用 5 个独立的 Workflow + LLM Provider 分片，并按 80% 扩展效率估算：

```text
0.2704 × 5 × 0.80 = 1.0816 份/s
```

因此可以表述为：

> 单分片完整评估吞吐达到 0.27 份/s；通过 Workflow Worker 与 LLM Provider 独立分片，按 80% 扩展效率进行容量规划，5 分片预计可支撑约 1.08 份/s，满足 1 QPS 目标。入口接收能力已实测达到 3.66 QPS。

## 口径边界

- `3.66 QPS` 是入口接收吞吐，不是完整报告完成吞吐；
- `0.2704 份/s` 是单分片完整 Workflow 实测吞吐；
- `1.0816 份/s` 是线性扩展容量估算；
- 1 QPS 集群实测需要补充多分片、充足 LLM 余额后的持续压测。
