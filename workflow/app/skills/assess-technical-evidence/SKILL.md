# 技术证据评估方法论

## 激活条件
- 候选人声称具体技术成就(QPS提升、延迟降低、架构迁移)
- JD要求特定技术栈专长
- 需要区分高级/专家级与中级技术深度

## 评估框架 (STAR+量化)

### 1. 声明提取
对简历中每个技术声明:
- **Situation**: 业务背景是什么?(团队规模、流量规模、遗留约束)
- **Task**: 需要解决什么具体技术问题?
- **Action**: 做了什么架构/实现决策，为什么?
- **Result**: 量化结果，含基线对比

### 2. 深度信号 (评分 1-5)
| 信号 | 初级(1-2) | 高级(3-4) | 专家(5) |
|------|-----------|-----------|---------|
| 具体性 | "用了Redis" | "Redis Cluster+sentinel做HA，5万QPS读缓存" | "设计多级缓存(L1本地+L2 Redis Cluster)，一致性哈希，错开TTL防雪崩" |
| 权衡意识 | 未提及 | 承认一个权衡 | 明确讨论CAP/成本/复杂度权衡，有数据支撑 |
| 规模指标 | 模糊("大规模") | 具体指标(QPS, P99延迟) | 系统级指标+业务影响关联 |
| 故障处理 | 未提及 | 提到错误处理 | 描述降级策略、混沌工程、事后复盘 |

### 3. 验证优先级
使用 `cn-web.search` 验证:
- 公司技术博客是否提到类似架构
- 开源贡献(GitHub, Gitee)是否匹配声称的专长
- 候选人的技术文章或会议分享
- 技术采用时间线(在职期间该公司是否已采用声称的技术?)

### 4. 红旗检测
- 声称的技术在其任职期间尚未发布
- 指标超出行业基准且无解释(如初创公司声称"99.999%可用性")
- 多个角色中出现完全相同的措辞(复制粘贴简历)
- 架构声明缺乏权衡讨论

### 5. 输出要求
每个技术领域产出结构化评估:
```json
{
  "domain": "分布式系统",
  "claimedLevel": "senior",
  "assessedLevel": "mid-to-senior",
  "confidence": 0.7,
  "evidence": ["具体声明及其验证状态"],
  "gaps": ["需要面试验证的领域"],
  "interviewProbe": "针对性验证问题"
}
```
